# Finance Core 3.2.0 validation and handoff

Product 3.2.0 retains API 3.1.1 (`/api/v3`), ledger schema 2, registry schema 1, FRAG plugin 1.0.0 and protocol 1. Work is FC-only. No real financial databases were opened, migrated or repaired; FRAG, Sorenst, KB and Mei were not modified. No commit, push, tag or deployment was performed.

## Changes

The English React application has seven business pages, original SVG identity, responsive pill navigation, contextual tabs, Journal/import confirmation steps and a keyboard-accessible Workspace selector. Forms retain strings for amounts, quantities and rates; all financial calculations remain in FC. Reads are bound to request generation, page and Workspace, obsolete reads are cancelled, and writes lock navigation and duplicate submission. Unsaved state is tracked per form; successful unrelated actions do not clear it. Validation becomes stale immediately after editing. One-time tokens are cleared on navigation and logout.

Workspace ledger access and global undo now share scope/status checks and a stable lifecycle lock. Archive, quarantine and control undo use the same lock. File movement is preflighted as a complete explicit-file plan and compensated when a move or Registry transaction fails. A missing active Vault returns a safe conflict without creating a replacement database. Older status undo cannot reactivate a quarantined Vault. Mutation undo is captured before releasing its operation lock.

Additional reproduced fixes cover operand-sized Decimal calculations in posting/reports/holdings, exact half-even lot allocations, ledger and Registry rollback on commit failure, recurring generation only on/after the actual calendar due date, and validation errors that previously echoed CSV input or batch identifiers. The schema and existing rounding policy remain unchanged. Due dates beyond a month's last day use that actual last day, including leap years; recurring generation still creates unposted drafts only.

## Manual use and limits

After configuring the local admin token as described in README, run `npm.cmd run dev`. Open the loopback URL shown by Vite (normally `http://127.0.0.1:5174`). Current production output is `dist/v3.2.0/`; it must be served with same-origin `/api/v3` forwarding to FC rather than opened as a file URL. Use an existing trusted loopback origin on port 5174 or 8788 for cookie writes. Serving/deployment was not performed.

Run the README verification commands to repeat deterministic checks. The synthetic browser tool requires the already-approved local Archify Chrome transport and an isolated FC backend on port 18788 behind Vite's `FC_UI_API_TARGET`; its default fixtures are synthetic only. Keep all generated profiles/screenshots under ignored `.tmp/`.

Lifecycle locks coordinate requests in one process. Use one writer process for a configured data root. Filesystem moves and SQLite commits cannot provide power-loss crash atomicity; unsuccessful compensation preserves files for manual review and does not auto-purge directories. Real-data migration or repair requires separate authorization. Backups retain the existing format/schema/hash/row-shape/foreign-key checks; a hash alone is not proof of trusted financial meaning.

Changes are unstaged. Review the exact Git file list and diff before manual staging. Agent instructions, command rules, private audit details, screenshots, credentials and data remain ignored; `.gitignore` alone never cleans previously tracked content. The final audit found no tracked ignored/rule/data files and an empty staged file list.
